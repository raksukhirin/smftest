## 3. สถานะ Post — **กรอง post ตามรายงาน** `[ตัดสินใหม่ 2026-07-22 · แทนที่ของ 2026-07-14]`

> ✅ **D12 ตามรายงาน** — `~~ไม่สนใจ posted~~` **ยกเลิก** เพราะขัดกับพฤติกรรมจริงของระบบเดิม
> เหตุผล: D12 ต้องเทียบกับตัวเลขที่ผู้ใช้เห็นอยู่ทุกวัน · ถ้านิยามต่างจากรายงาน จะอธิบายส่วนต่างไม่ได้เลย

สูตรใน `SFDPFJOB01_CONSOL.rpt` (`n_billrev_thb_consol` / `n_vchr_thb_consol`) เริ่มด้วย:

```
If isnull({ARINVDETAIL.DETID}) then Formula = 0     ← ยังไม่ post → ไม่นับ
ElseIf {ARINVHEAD.POSTENTRY}=3   then Formula = 0     ← ยกเลิก post → ไม่นับ
```

**แต่บรรทัดโอน `DOCTYPE='N/A'` ถูกบวกต่อท้าย นอกด่านนี้** → นับเสมอแม้ยังไม่ post
(นี่คือเหตุผลที่ `COMINS 100` ซึ่ง `THBAMT` เป็น null ยังโผล่ในรายงาน)

### กฎที่ D12 ใช้

```
นับบรรทัดเมื่อ:  DOCTYPE='N/A'                            ← นับเสมอ (บรรทัดโอน)
             หรือ  ARINVDETAIL.DETID IS NOT NULL
                   AND ARINVHEAD.POSTENTRY <> 3           ← post แล้วและไม่ถูกยกเลิก
เงื่อนไขเดียวกันใช้กับกองที่นำไปเฉลี่ย (allocation pool) ด้วย
```

**ผลกระทบที่ต้องรับ 3 ข้อ:**

| # | ผล |
|---|---|
| 1 | **D12 ต้อง join `ARINVDETAIL`/`ARINVHEAD`** — เหตุผล "ไม่แตะ financial table เลย" (§2) **ไม่จริงอีกต่อไป** · แต่แตะแค่ **อ่านสถานะ post** ไม่ได้เอายอดเงินมาใช้ |
| 2 | **actual จะขยับตามเวลา** — งานที่ยังไม่วางบิลจะยังไม่ปรากฏ → ต้องแสดง **as-of / ความครบถ้วน** ทุกครั้ง ห้ามให้เข้าใจว่านิ่งแล้ว |
| 3 | **ยอด actual ต่ำกว่าความจริงชั่วคราว** — ไม่ใช่บั๊ก แต่ต้องมีธงบอก (เช่น "มี n บรรทัดรอ post") |

> `[คงเดิม]` **ยังไม่เอา *ยอดเงิน* จาก `ARINVDETAIL`** — เงินยังอ่านจาก `OPTRANSDETAIL` ตาม §2
> ที่เปลี่ยนคือ **ใช้ `ARINVDETAIL` เป็นด่านกรองสถานะเท่านั้น**

### FX: ใช้ `SALERATE` ไม่ใช่ `ITEMRATE` `[แก้ 2026-07-22 รอบ 2]`

```
ยอด THB ต่อบรรทัด = (ITEMTYPE='ADV' ? THBTOT : THBAMT) × DOCBAL
ถ้า THBAMT เป็น null (ยังไม่ post) → CALAMT × SALERATE × DOCBAL
```

หลักฐาน: บรรทัด `PROS` มี `ITEMRATE = 1` แต่ `SALERATE = 32.2314` →
`CALAMT 5 × 32.2314 = 161.16` = `THBAMT` ✓ (ถ้าใช้ `ITEMRATE` จะได้ 5 ผิด)

> ⚠ **รอบแรกเขียนว่า FX คือ `SALETEXTRATE` — ผิด** · ทั้งสองคอลัมน์เก็บค่าเดียวกัน
> (`SALETEXTRATE` เป็น *text* mirror ของ `SALERATE`) จึงบังเอิญคำนวณออกมาถูก
> **สูตรใน .rpt ใช้ `SALERATE` เป็นตัวคูณ · `SALETEXTRATE` ใช้เป็น marker เท่านั้น** (ดูหัวข้อถัดไป)

### `SALETEXTRATE` = **ราคาโอน** ไม่ใช่ธง และไม่ใช่ BadFx `[ผู้ใช้สาธิต 2026-07-22]`

> **`[แก้รอบ 4]` เดิมเรียกว่า "ธง" — ยังไม่ตรงนัก · มันคือ *ตัวเลขราคา* ที่ Consol ขายให้ Sale**
> `'0'` ไม่ใช่ flag พิเศษ แต่คือ **"ขายให้ในราคา 0"** — สามสถานะจึงตกมาจากความหมายเดียวกัน

> → ส่วนเฉลี่ยเป็น 0 ทุก house ทันที
>
> ⚠ **ควบคุมทีละบรรทัด — ไม่มีสวิตช์ระดับ job หรือ house**
> → ปิดบางบรรทัดได้ และระบบเดิม**ไม่เตือน** · FPI ต้องแสดง `เฉลี่ย n/m บรรทัด` เสมอ (ทำใน mockup แล้ว)

เป็น **marker 3 สถานะที่ผู้ใช้ตั้งเอง** — ไม่ใช่ผลข้างเคียงของ FX

แต่เป็น **com price ของบรรทัดนั้นมีค่า 100 และ com price ไม่ถูกกรอง post**
→ `n_vchr_thb_tot = 100` → `n_vchr_n_a_consol = −100` → Consol Revenue `+100` (กลไก ②)

### ความหมายเชิงธุรกิจ `[ผู้ใช้ยืนยัน 2026-07-22]`

- **No-House:** `[แก้ 2026-07-17]` job แบบไม่มีแถว `Direct` เลย → ยอดค้างบนแถว `Allocated` ซึ่ง map 1:1 กับ job อยู่แล้ว
  → **ไม่ต้องเฉลี่ย** (ไม่ใช่ "house เดียวรับ 100%" ตามที่ร่างเดิมเขียน — **ไม่มี house ปลายทางให้ลง**)
- **Basis ตรงกับ dimension ที่ FPI model ไว้แล้ว** ใน `rate_charges.basis` → ไม่ต้องคิดมิติใหม่

### ⚠ `SFJOB.TOTBL` — เสนอเลิกใช้เป็นตัวหาร `[2026-07-17 · ต้องรับรอง]`

`TOTBL` = จำนวน **Direct** house — **ไม่นับแถว master** (`SE17050002`: TOTBL=5, Direct=5, +1 `Allocated` = 6 แถว)

> **→ เปลี่ยนตัวหารเป็น `COUNT(SFHBL WHERE JOBNO=? AND DOCTYPE='Direct')`**
>
> **เหตุผลเชิงโครงสร้าง (ไม่ใช่สถิติ):** `TOTBL` เป็น counter ที่ denormalize ไว้ และ **DB ไม่มี FK/constraint
> บังคับให้ตรงกับจำนวนแถวจริง** → มีโอกาสไม่ตรงโดยไม่มีอะไรจับ · ขณะที่สิ่งที่สูตรต้องการคือ
> "จำนวน house ที่มีอยู่ให้เฉลี่ยลง" ซึ่ง COUNT ตอบตรงและ**มีค่าเสมอ**
>
> **ข้อโต้แย้งที่ต้องเคลียร์ก่อนรับรอง:** เป็นไปได้ว่า `TOTBL` ตั้งใจหมายถึง *"จำนวน B/L ที่วางแผนไว้"*
> ไม่ใช่ *"ที่สร้างจริง"* — ถ้าใช่ ทั้งสองตัวตอบคนละคำถาม และต้องเลือกโดยรู้ตัว
>
> 🔲 **ความถี่ที่ `TOTBL` ไม่ตรงจริง → ต้องวัดบน production** (`SMF_DEMO` ตอบไม่ได้)

**`[D12(d)] ตัดสินแล้ว 2026-07-14:` สร้าง stored proc allocation ใหม่ — ไม่ reverse-engineer ของเดิม**

### Fallback เมื่อหารไม่ได้ `[ตัดสินแล้ว 2026-07-14]`

เมื่อตัวหารเป็น 0/null (เช่น `SUM(CBM)` ของทุก house = 0 หรือ house ไม่กรอก CBM):

```
weight ปกติ  →  ถ้าตัวหาร = 0/null  →  ตกไปใช้ SHIP (หารเท่า = master ÷ SFJOB.TOTBL)
                                        + ติดธงเตือน "allocation fallback" ที่บรรทัดนั้น
```

- **ห้ามเงียบ** — ธงต้องขึ้นถึง UI/รายงาน เพราะยอดที่เฉลี่ยแบบ fallback ไม่ใช่ความจริงเชิง UOM
- ถ้า `TOTBL` เองเป็น 0/null → **ไม่เฉลี่ย** ปล่อยยอดค้างที่แถว master + ธง error (fail-loud ตามแนว D3 fail-closed)

## 5. Roll-up ถึง Booking `[ตัดสินแล้ว 2026-07-14]`

> **ใช้เส้นทาง (b) — ผ่าน house** · เก็บ (a) ไว้เป็น **cross-check** ไม่ใช่ทางหลัก

| เส้นทาง | Join | สถานะ |
|---|---|---|
| **(b) ผ่าน house** ✅ | `OPTRANSDETAIL.HBLREF → SFHBL.DOCNO` → `SFHBL.BOOKREF = SFBOOK.DOCNO` | **ทางหลัก** — house คือ grain ที่ allocation (§4) ทำงาน ต้องเฉลี่ยแถว master ก่อนแล้วค่อย roll up |
| (a) ตรง | `OPTRANSDETAIL.REFBOOK = SFBOOK.DOCNO` | **cross-check** — แถว `Allocated` ผูก job ไม่ใช่ booking เดียว → ใช้เป็นทางหลักไม่ได้ |

**เหตุผลที่ (a) เป็นทางหลักไม่ได้:** แถว master (`DOCTYPE='Allocated'`, `DOCNO=JOBNO`) เป็นของ **job** ทั้งใบ —
ถ้า roll up ตรงด้วย `REFBOOK` ยอด master จะตกไป booking เดียว (หรือหาย) แทนที่จะกระจายตาม UOM

### กฎ roll-up — แยกตามจำนวน booking ของ job

**ข้อเท็จจริงจาก `SE17050002`:** แถว `Allocated` มี `SFHBL.BOOKREF` เป็น **ค่าว่าง**
ขณะที่ Direct ทั้ง 5 แถวถือ `BSE17050004`
→ กฎ roll-up จึงอิง `BOOKREF` ของแถว master ไม่ได้

**กฎ roll-up ที่ควรเป็น — แยกตามจำนวน booking ของ job:**

| job มี booking | ทำอะไร | ต้องเฉลี่ยไหม |
|---|---|---|
| **1 ใบ** | **Σ ทั้ง job → booking นั้น** · ไม่พึ่ง `BOOKREF` ของ master | ❌ **ไม่ต้อง** |
| **≥2 ใบ** | เฉลี่ย master ลง Direct ตาม UOM → roll up ด้วย `BOOKREF` ของ house | ✅ **ต้อง — กฎที่ต้อง sign-off (§10 ครึ่ง B)** |
| **0 ใบ** | ไม่มี actual ระดับ booking (รายงานได้แค่ระดับ job) | — |

> **นัยสำคัญ:** กฎเฉลี่ยที่พิสูจน์ไม่ได้ **ไม่ได้กระทบทุก console job** อย่างที่ร่างนี้เคยเข้าใจ
> — กระทบเฉพาะ **job ที่มีหลาย booking** เท่านั้น · console ที่มี booking เดียวไม่ต้องเฉลี่ยเพื่อ roll-up เลย
> → **ขอบเขตของ §10 ครึ่ง B แคบลงมาก** (ดู §10)

🔲 **ยังต้องพิสูจน์ (ไม่ใช่ blocker):** query เทียบ (a) vs (b) บน console job (`SE17050002` / `BSE17050004` → 6 house)
— ส่วนต่างที่เจอควรอธิบายได้ด้วยยอด master ที่ยังไม่เฉลี่ยเท่านั้น

## 6. แผนที่สูตรทั้งชุด `[เขียนใหม่ 2026-07-22 รอบ 4 — แทนที่ฉบับที่เดาเอง]`

> 📁 **ตัวสูตรดิบอยู่ที่ [`reference/SFDPFJOB01_CONSOL.formulas.md`](./reference/SFDPFJOB01_CONSOL.formulas.md)**
> (คัด verbatim 41 ตัว จัดกลุ่มตาม 4 ชั้น) · dump เต็มที่ `reference/SFDPFJOB01_CONSOL.dump.txt`
> **หัวข้อนี้คือคำอธิบาย — ไม่ต้องเปิด `.rpt` ใหม่**
>
> **ฐานะของหัวข้อนี้:** เป็น**สูตรของระบบเดิมที่แกะออกมา** ไม่ใช่สูตรที่ FPI คิดขึ้น
> `[ผู้ใช้กำหนด]` **ยึดสูตรใน `.rpt` เป็นนิยามตั้งต้น** — ไม่ต้องไล่ว่ายอดเงินควรมาจากตารางไหน
> ฉบับก่อนหน้าเขียนว่า `Sold = Σ THBAMT×DOCBAL` ซึ่ง**ง่ายเกินจริงไปมาก** — ถอนออกแล้ว

### โครง 4 ชั้น

```
ชั้น 1  ยอดต่อบรรทัด       nDetGross / nDetTotal × nDocBal
ชั้น 2  แยกประเภท          Bill/Cost × ADV/REV/COS × EXPCODE (KB, R/F)
ชั้น 3  ชั้น "Saleperson"   ราคาโอนทับยอด invoice + ตัดสินว่าเข้าฝั่ง Sale หรือ Consol
ชั้น 4  ชั้น Allocated      เฉลี่ยยอด master ลง Direct house
```

**ชั้น 3 คือหัวใจ** — และเป็นชั้นที่ร่างก่อน ๆ ของเอกสารนี้มองข้ามทั้งหมด

### ชั้น 1 — ยอดต่อบรรทัด

```
nDetGross = IIF({@isVATIO}, THBTOT, THBAMT)
nDetTotal = THBTOT
nDocBal   = Bill ? IIF(SRCTYPE='AR',1,-1) : IIF(SRCTYPE='AP',1,-1)
nDocBalOP = DOCTYPE='CN' ? -1 : 1            ← ใช้เฉพาะฝั่งราคาโอน
```

| ข้อสังเกต | ผล |
|---|---|
| **`{@isVATIO}` ถูก hardcode เป็น `False`** (โค้ด `VATINOUT=1` ถูกคอมเมนต์ทิ้ง) | สาขา VAT ในชั้นนี้ **ตายแล้ว** → `nDetGross` = ยอดก่อน VAT เสมอ |
| **`nDocBal` ไม่ใช่คอลัมน์** | เป็น sign ที่ได้จาก `SRCTYPE` — Bill ที่ไม่ใช่ AR / Cost ที่ไม่ใช่ AP จะกลับเครื่องหมาย = กลไกหัก CN |
| ทุกสูตรฐานเปิดด้วยด่านเดียวกัน | `isnull(ARINVDETAIL.DETID) → 0` · `POSTENTRY=3 → 0` |

### ชั้น 2 — แยกประเภท (ยังไม่มีชั้น Saleperson)

| สูตร | เงื่อนไข | ยอดที่ใช้ |
|---|---|---|
| `n_billrev_thb` | Bill · ≠ADV · `EXPCODE≠'KB'` | `nDetGross` |
| `n_billref_thb` | Bill · ≠ADV · `EXPCODE='R/F'` | `nDetGross` |
| `n_billadv_thb` | Bill · **ADV** | `nDetTotal` |
| `n_vchr_thb` | Cost · ≠ADV · `EXPCODE≠'KB'` | `nDetGross` |
| `n_vchr_kb` | Cost · ≠ADV · `EXPCODE='KB'` | `nDetGross × (DOCTYPE='DN' ? 1 : −1)` |
| `n_vchradv_thb` | Cost · **ADV** | `nDetTotal` |

> ⚠ **`R/F` เข้าเงื่อนไขทั้ง `n_billrev_thb` และ `n_billref_thb`** → บวกซ้ำ (งานเปิดข้อ 20)
> ⭐ **ADV มีสายของตัวเอง — ไม่ผ่านชั้น Saleperson และไม่ผ่านราคาโอน** `[แก้ 2026-07-22 รอบ 5]`
>
> ```
> Sale Revenue = [n_billref_thb + n_billrev_thb] ผ่านชั้น 3  +  n_billadv_thb ตรง ๆ
> Sale Cost    = [n_vchr_thb + n_vchr_kb]        ผ่านชั้น 3  +  n_vchradv_thb ตรง ๆ
> ```
>
> **หลักฐานชี้ขาด:** บรรทัด `VISE26070002` (Cost · `ITEMTYPE='ADV'` · `SALEPRICE=1,121.50` · `THBTOT=1,200`)
> ขึ้นรายงานเป็น **1,200** = `nDetTotal` · ถ้าผ่านราคาโอนจะได้ 1,121.50
> → ฝั่ง Bill ก็หลักการเดียวกัน แค่ job นี้ `QTY×SALEPRICE = THBTOT` พอดี จึงแยกไม่ออก
>
> 🔲 **ยังไม่ได้พิสูจน์:** ADV บน house ที่เป็นของ Consol เข้าคอลัมน์ไหน — mockup กันไว้ที่ฝั่ง Consol
> ตามหลักแบ่งแผนก (ใบนี้ไม่มีบรรทัดตัวอย่าง)

### ชั้น 3 — ชั้น Saleperson (ตัวตัดสิน Sale vs Consol)

เปิดใช้เมื่อ `?chgGroup1="Saleperson"` และ `?chgGroup2="House B/L"`

```
n_billrev_thb_net = n_billref_thb + n_billrev_thb + n_billadv_thb
n_vchr_thb_tot    = n_vchr_kb + n_vchr_thb
   ↓ แล้วครอบด้วย
   Trim(SALETEXTRATE)='0'          → 0            ขายให้ 0 บาท
   SFHBL.SALENO = SFHBL_M.SALENO   → 0            house เป็นของ Consol เอง
   n_bill_com <> 0                 → n_bill_com   ★ ราคาโอนทับยอด invoice
   มิฉะนั้น                          → ยอด invoice
```

**ราคาโอน — จุดที่แปลกที่สุดในรายงาน**

```
n_bill_com / n_cost_com =
   SALETEXTRATE null/''/'0' → 0
   มิฉะนั้น  nDocBalOP × QTY × SALEPRICE × IIF(ITEMCURR='THB', 1, SALERATE)
   ยกเว้น VATINOUT=1 → กลับไปใช้ nDetGross/nDetTotal
   (ฝั่ง Cost ตัด EXPCODE='KB' ออก — KB ใช้ n_cost_com_na แยก)
```

- **ไม่มีด่าน post** → บรรทัดที่ยังไม่วางบิลเข้าฝั่ง Sale ได้ ถ้ามีราคาโอน
- ฐานคือ **`SALEPRICE`** ไม่ใช่ยอด invoice → นี่คือ *ราคาที่ Consol ขายให้ Sale* จริง ๆ
- ⚠ `n_bill_com` **เช็ค `VATINOUT` โดยตรง** ไม่ผ่าน `{@isVATIO}` → สาขา VAT ที่นี่ **ยังทำงานอยู่**

**ฝั่ง Consol = เงื่อนไขเดียวกันแต่กลับด้าน**

```
n_billrev_thb_consol / n_vchr_thb_consol =
   post guard เดิม
   SALENO = SFHBL_M.SALENO  →  นับ
   หรือ Trim(SALETEXTRATE)='0' →  นับ
   มิฉะนั้น → 0
   + บรรทัดโอน N/A (นอก post guard — ดูกลไก ② §4)
```

### ชั้น 4 — Allocation

```
xBillRevThb_Alloc = _cbm + _shp + _kgs + _do     (ฝั่ง Cost = xVchrThb_Alloc โครงเดียวกัน)

ข้ามทั้งหมดเมื่อ : SUB_SYSNAME ∈ {CS, TS}  หรือ  SFJOB.TOTBL ≤ 1
ต้นทาง          : OPTRANSDETAIL.HBLREF = JOBNO เท่านั้น (แถว master)
ธง              : chgGroup1='Saleperson' And Trim(SALETEXTRATE)='0' → 0
                  'ไม่ให้มี Real Allocate   ← คอมเมนต์ของผู้เขียนรายงานเอง

น้ำหนัก:
  _shp : × 1 ÷ SFJOB.TOTBL                          (null/0 → คืนยอดเต็ม)
  _cbm : × {@n_cbm} ÷ SFJOB.(REVTON|CBM)
         {@n_cbm} = ?AvgType='REV/TONs' ? SFHBL.REVTON : SFHBL.CBM · isHideHBL → 0
  _kgs : × SFHBL.GW ÷ SFJOB.GW                      (GW=0 → คืนยอดเต็ม)
  _do  : × SFHBL.TOTDO ÷ SFJOB.TOTDO
  Round(share, 2) ต่อ share
```

**⭐ สองสายคู่ขนาน — ราคาโอนแทรกชั้นนี้ด้วย**

| สาย | ตัวแปร | ฐาน | เลือกเมื่อ |
|---|---|---|---|
| **Real Allocate** | `n_BillAvg_*` / `n_Cost_*` | ยอด invoice (`nDetGross`) | `SALETEXTRATE` ว่าง/null |
| **Com Allocate** | `n_BillAvgCom_*` / `n_CostCom_*` | `QTY × SALEPRICE` | `SALETEXTRATE` มีค่า |
| — | — | **0** | `SALETEXTRATE = '0'` |

> **โครงเดียวกับชั้น 3 เป๊ะ** — `SALETEXTRATE` ไม่ได้คุมแค่ว่า "เฉลี่ยไหม" แต่คุมด้วยว่า
> **เฉลี่ยจากยอดไหน** · สาย Com **ไม่มีสาขา `VATINOUT`** (ต่างจากชั้น 3)

### 4 สูตรที่ประกอบเป็นตาราง Profit by House

| | Revenue | Cost |
|---|---|---|
| **Sale Dept** | `n_billrev_thb_net` + `xBillRevThb_Alloc` | `n_vchr_thb_tot` + `xVchrThb_Alloc` |
| **Consol Dept** | `n_billrev_thb_consol` | `n_vchr_thb_consol` |

### ต่อยอดเป็น margin (ส่วนนี้เป็นของ FPI ไม่ใช่ของรายงาน)

```
ต่อ booking    = Σ house ที่ SFHBL.BOOKREF = booking นั้น    (ดู §5)
Margin_actual  = Sold_actual − Cost_actual + KB_actual        (สูตรเดียวกับ D3)
Margin%_actual = Margin_actual × 100 / (Sold_actual + KB_actual)
Variance       = Margin%_actual − MARGINPCN (ที่ approve ตอน Confirm)
```

> **FX:** ไม่ต้องคูณเอง — ยอดที่ชั้น 1 ให้มาเป็น THB แล้ว
> ยกเว้น**สายราคาโอน** ที่ต้องคูณ `SALERATE` เอง (`ITEMCURR ≠ 'THB'`)

### 3 ข้อสรุปที่ได้จากการอ่านทั้งชุด

1. **`SALETEXTRATE` คือแกนกลางของทั้งรายงาน** — ตัดสิน 3 อย่างพร้อมกัน: ยอดเป็นเท่าไหร่ · เข้าฝั่งไหน · เฉลี่ยหรือไม่ · และเป็นเหตุผลที่ด่าน post รั่วได้ (ราคาโอนไม่มีด่าน post)
2. **Allocation เป็นเครดิต ไม่ใช่การโอน** — เข้า Sale โดยไม่หักจาก Consol · เงินก้อนเดียวปรากฏสองที่โดยตั้งใจ
3. **ไม่มีอะไร persist** — ทั้ง allocation และการแบ่งแผนกคำนวณตอนพิมพ์ · `ALLOCAMT` ว่างเพราะไม่เคยถูกใช้ → **นี่คือช่องว่างที่ FPI เติมได้จริง:** ทำให้ตัวเลขชุดนี้ตรวจย้อนหลังได้ แทนที่จะมีชีวิตอยู่แค่ตอนกดพิมพ์

**ขอบเขตของ "ของอนุมาน" — แคบกว่าที่ร่างนี้เคยเขียน `[แก้ 2026-07-17]`**

| job มี booking | ของแข็ง | ของอนุมาน |
|---|---|---|
| 1 ใบ | **ทั้งหมด** (Σ ทั้ง job → booking นั้น) | — |
| ≥2 ใบ | cost ตรงของ house | **ส่วนแบ่งจากแถว master** |

> **สัดส่วนรายใบยังต้องแสดงเสมอ** — แต่มันคือคุณสมบัติของ *booking นั้น ๆ* ไม่ใช่ตัวเลขรวมของทั้งระบบ
>
> 🔲 **มี job หลาย booking มากแค่ไหน / คิดเป็นเงินเท่าไหร่ → ต้องวัดบน production**
> (`SMF_DEMO` ตอบไม่ได้ — เคยมีตัวเลข 94%/6% เขียนไว้ตรงนี้จาก demo แล้วพบว่าใช้ไม่ได้ทั้งตัวเลขและเหตุผล)
>
> **ตัวเลขนี้คือสิ่งที่กำหนดเดิมพันของ sign-off ครึ่ง B ทั้งหมด** — ถ้าน้อย งานนี้เกือบไม่มีความเสี่ยง
> ถ้ามาก ต้องคุยกันจริงจัง · **เป็นเหตุผลอันดับ 1 ที่ต้องต่อ production ให้ได้ก่อน**

### ~~🔲 ทางเลือกที่ยังเปิด — จำกัด scope แทนการอนุมาน~~ → **ไม่จำเป็นแล้ว** `[2026-07-22]`

> D12-lite เกิดขึ้นเพื่อหลบ "กฎเฉลี่ยที่พิสูจน์ไม่ได้" — **เหตุผลนั้นหมดไปแล้ว**
> กฎเฉลี่ยคือสูตรของระบบเดิมที่แกะออกมาได้และเทียบรายงานตรง → **ไม่ต้องแลก coverage ทิ้ง**
> เก็บไว้เป็นทางถอยเฉพาะกรณีที่ข้อ 16 (path `_cbm`/`_kgs`/`_do`) พิสูจน์ไม่ผ่าน

<details><summary>ข้อความเดิม (เก็บไว้เป็นประวัติ)</summary>

ถ้ายอมรับกฎเฉลี่ยใหม่ไม่ได้ (หรือยังไม่พร้อมเซ็น):

> **D12-lite: รายงาน actual เฉพาะที่พิสูจน์ได้**
> - **Job level** → actual จริง (พิสูจน์ได้ด้วยครึ่ง A)
> - **Booking level** → รายงานเฉพาะ **No-House/Direct (job:house = 1:1)** ซึ่งแม่นโดยไม่ต้องเฉลี่ย

> **D12-lite ที่นิยามใหม่:** รายงาน actual ระดับ booking สำหรับ **job ที่มี booking เดียว** (ไม่ว่าจะ console หรือไม่)

## 9. ลำดับงานถัดไป (เสนอ)

```
1. ปิด §8 ข้อ 1–2 (รับรอง + พิสูจน์ roll-up)      ← ต้องมี DB
2. Engine: คำนวณ actual + allocation (ไม่แตะ DOM, ทดสอบใน Node เหมือน engine อื่น)
3. Verify: เทียบ job จริงหลายใบ (console + no-house)
4. UI: เพิ่มฝั่ง Actual/Variance ในหน้า Booking Gate (3) + KPI variance ใน Dashboard (5)
        + (ถ้าจำเป็น) หน้า allocation breakdown master→house
```

**เหตุผลที่ engine มาก่อน UI:** ที่ผ่านมา engine-first จับ data bug ได้ตั้งแต่ยังไม่มีหน้าจอ (เช่น `margin_rules.validFrom`) — และ §8 ที่ยังเปิดอยู่อาจเปลี่ยนตัวเลข ถ้าทำ UI ก่อนต้องรื้อ
